# پرامپت نهایی: «کارنما» (Karnama) — سیستم مدیریت کار آژانس سوشال مدیا

> این پرامپت را کامل به Claude Code بده. اول `CLAUDE.md`، بعد `docs/PROJECT_MAP.md`، بعد همین فایل و `docs/SKILLS.md` را بخواند، و مرحله‌به‌مرحله (بخش ۱۶) جلو برود.
> «کارنما» اسم کاری پروژه است. اسم، لوگو و رنگ واقعی برند از پنل ادمین تنظیم می‌شود (White-label).

## ۰. نقش تو (تیم سه‌نفره)

قبل از هر تصمیم مهم، سه نقش نظر می‌دهند:

1. **مدیر عملیات (Ops Lead):** هر صفحه باید کار روزانه‌ی ادمین، کارگر یا مشتری را **کوتاه‌تر** کند. هر کاری که بیش از ۳ لمس لازم دارد، دوباره طراحی شود.
2. **مدیر طراحی (Creative Director):** مدرن، تمیز، حس «ابزار حرفه‌ای»؛ روی گوشی ارزان و اینترنت ضعیف ایران سریع.
3. **مدیر فنی (CTO):** امن، دقیق در ساعت و داده، تست‌پذیر، تحمل ۱۰۰۰ کاربر همزمان، و قابل فروش به آژانس‌های بعدی.

## ۱. تحلیل مشتری

- **کسب‌وکار:** نمایندگی شیراز آکادمی معین فرجی — اینستاگرام مارکتینگ و مدیریت سوشال مدیا برای کسب‌وکارها (B2B). اجرا در شیراز، مشاوره در شهرهای دیگر.
- **تیم:** زن و شوهر ادمین (هم مدیریت می‌کنند، هم گاهی خودشان کار انجام می‌دهند). کارگرها: تدوین ویدیو، عکس و متن‌نویسی، کار با هوش مصنوعی. **فقط ادمین با مشتری در تماس است**، کار را می‌گیرد و پخش می‌کند.
- **مشتری‌ها:** بیشتر مغازه‌دارها. دو نوع:
  1. **پیج کامل دست آژانس:** آژانس پست می‌سازد و خودش منتشر می‌کند.
  2. **پیج دست خود مشتری:** آژانس فایل، کپشن و **ساعت انتشار** را می‌فرستد و مشتری خودش منتشر می‌کند.
- **خدمات:** تولید محتوا، مدیریت پیج، تبلیغات (از جمله تبلیغ نزد اینفلوئنسرها) به خواست مشتری. **فقط اینستاگرام نیست:** تلگرام، ایتا، بله، روبیکا و هر شبکه‌ی دیگر (لیست شبکه‌ها دینامیک).
- **درآمد هر مشتری:** ماهانه ۸ تا ۱۲۰ میلیون تومان. هدف خودشان از سیستم: **«نظم داخلی»**.
- **رقبا (شیراز):** رسول ناصری، امیرارسلان قهاری (بیزینس منتور)، و آژانس‌های کوچک‌تر (marketingnazanin، rabin.content، akp.studioo). **هیچ‌کدام پنل پیگیری برای مشتری ندارند** → پنل مشتری مزیت فروش آژانس است.

### نیازهای کشف‌شده (Pain Points)
1. کارها در واتساپ و دفترچه گم می‌شوند → **تابلوی کار لایو** با مسئول، ددلاین و وضعیت.
2. معلوم نیست چه کسی الان روی چه کاری است و چقدر کار کرده → **ثبت دقیق ساعت کار و تایمر هر کار**.
3. غیبت و تأخیر ثبت نمی‌شود → **سناریوی کامل حضور و غیاب** با دلیل و زمان.
4. مشتری مدام می‌پرسد «کار من کجاست؟» → **پنل مشتری با پیشرفت لحظه‌ای**.
5. پست‌های «پیج دست مشتری» دیر یا اصلاً منتشر نمی‌شوند → **یادآوری انتشار سر ساعت + دکمه‌ی «منتشر کردم»**.
6. پکیج‌های فروش فقط در ذهن ادمین است → **پکیج‌های فروش با فیلدهای مناسب و توضیحات**، و مصرف هر پکیج.
7. هر خدمت جدید یعنی تغییر کد → **همه‌چیز دینامیک** (خدمت، مراحل، نقش، فیلد، زبان، محتوا).

## ۳. قوانین کلی (از `docs/SKILLS.md` — اجباری)

- رابط کاربری **فارسی و RTL** (و هر زبان دیگری که ادمین اضافه کند). کد، نام‌ها و کامنت‌ها انگلیسی. جواب‌ها به امیر **فارسی**.
- **هیچ امضای AI** در کامیت، PR یا فایل‌ها. هیچ `Co-Authored-By`.
- **هیچ کلید یا رمزی در کد.** User Secrets / متغیر محیطی / `.env`. کلید لازم خالی = برنامه با پیام روشن اجرا نشود.
- هر مرحله: کد → تست → build سبز → **تست CRUD تصویری** (بخش ۱۵) → به‌روزرسانی `docs/PROJECT_MAP.md`. تا سبز نشده، مرحله‌ی بعد نه.
- همه‌ی متن‌ها، نام‌ها و اعداد نمونه **دمو** هستند و از پنل قابل تغییرند.
- قیمت‌ها و پیشنهادهای فروش **هرگز** داخل ریپو نروند.

## ۴. معماری

```
Karnama.sln
├── src/
│   ├── Karnama.Domain/          # Entities, Value Objects, State Machines, قوانین (بدون وابستگی)
│   ├── Karnama.Application/     # Use cases, DTO (record), FluentValidation (پیام فارسی), Permissions
│   ├── Karnama.Infrastructure/  # EF Core (PostgreSQL), Redis, Storage (S3 ابرآروان), SMS, Bots, Push, Outbox
│   ├── Karnama.Api/             # REST /api/v1 + SignalR Hubs + Auth + RateLimit
│   ├── Karnama.Worker/          # Hangfire: یادآوری‌ها، تشخیص غیبت، Outbox، پردازش فایل، بکاپ
│   └── karnama-web/             # Next.js (App Router) + TS + Tailwind + shadcn/ui — فقط 21st.dev
├── mobile/                      # Capacitor 8: android/ (پروژه‌ی Android Studio)
├── tests/
│   ├── Karnama.UnitTests/
│   ├── Karnama.IntegrationTests/   # Testcontainers (PostgreSQL + Redis واقعی)
│   ├── e2e/                        # Playwright تصویری (دسکتاپ + موبایل)
│   └── load/                       # k6: ۱۰۰۰ کاربر همزمان
├── deploy/                      # docker-compose.prod.yml, nginx, backup
└── docs/  tools/
```

**تصمیم‌ها (در لاگ تصمیم نقشه ثبت شده):**
- **PostgreSQL** به‌جای SQL Server: بدون هزینه‌ی لایسنس روی سرور ایران، و EF Core کامل پشتیبانی می‌کند.
- **Next.js با دو خروجی از یک کد:** وب (SSR برای صفحه‌ی عمومی و پنل‌ها) و **خروجی استاتیک** (`output: 'export'`) برای داخل اپ اندروید. صفحات پنل باید **Client-side data fetching** باشند تا در هر دو خروجی کار کنند. صفحه‌ی عمومی/معرفی فقط در وب.
- **Capacitor 8** برای اندروید: یک کد UI، پروژه‌ی واقعی Android Studio، دسترسی به دوربین، فایل، اعلان و ذخیره‌ی امن.
- **SignalR** با پروتکل **MessagePack** برای لایو، **Redis backplane** برای چند نمونه‌ی API.
- **Hangfire** روی سرویس جدای `Karnama.Worker` تا کار سنگین API را کند نکند.

## ۵. استاندارد بک‌اند — `backend-dotnet-skills-bundle` (اجباری)

همه‌ی ۱۰ بخش `docs/SKILLS.md` بخش ۲ اجرا شود. نکات ویژه‌ی این پروژه:

1. **معماری تمیز:** قوانین داخل Entity (`workItem.Start(workerId, now)`، `shift.ClockOut(now)`، `absence.Approve(adminId)`). `Result<T>`، `CancellationToken` همه‌جا.
2. **ماشین‌های وضعیت صریح** (انتقال غیرمجاز = خطا، و هر انتقال در Audit):
   - **سفارش مشتری (Order):** `Requested → Accepted → InProgress → AwaitingClientApproval → Approved → Scheduled → Published → Done` (+ `ChangesRequested` برمی‌گردد به `InProgress`، + `Cancelled`)
   - **کار (WorkItem، یک مرحله از سفارش):** `Todo → Assigned → Running ⇄ Paused → Submitted → (Rejected → Running) → Accepted`
   - **شیفت (Shift):** `Scheduled → ClockedIn ⇄ OnBreak → ClockedOut` (+ `Missed`)
   - **غیبت/مرخصی (Absence):** `Detected|Requested → ReasonSubmitted → Approved|Rejected` (+ `Cancelled`)
   - **انتشار (PublishJob):** `Pending → Reminded → PublishedByClient|PublishedByAgency` (+ `Overdue`)
3. **EF Core:** `AsNoTracking` + Projection، بدون N+1، **Keyset Pagination** برای لیست‌ها. `xmin` (RowVersion در PostgreSQL) روی `WorkItem`، `Shift`، `TimeEntry`، `Absence`، `ClientPackage`، `Order` → تعارض = 409 با پیام فارسی.
   - **ضمانت دیتابیسی:**
     - هر کارگر هم‌زمان **فقط یک تایمر فعال** (`UX_TimeEntries_OneRunningPerUser` روی `EndedAt IS NULL`).
     - هر کارگر هم‌زمان **فقط یک شیفت باز** (`UX_Shifts_OneOpenPerUser`).
   - **ساعت:** همه‌ی زمان‌ها `timestamptz` (UTC) و نمایش در `Asia/Tehran`. **مدت‌ها به ثانیه با `long`**؛ هرگز `double`.
   - پول (قیمت پکیج) `long` به **ریال**؛ نمایش تومان.
   - Soft Delete، فیلدهای Audit، جدول‌های Append-only برای `TimeEntryEvents` و `AuditLog`.
4. **REST:** `/api/v1/...`، `201/204/409/422`. OpenAPI فقط Development.
5. **اعتبارسنجی:** FluentValidation با پیام فارسی (و کلیدهای ترجمه برای زبان‌های دیگر). `ProblemDetails` با `traceId`.
6. **سرعت و Real-time:** بخش ۸، ۱۱ و ۱۲.
7. **تست:** بخش ۱۵.
8. **DevOps:** Docker چندمرحله‌ای non-root، Compose با Health Check، CI با `dotnet list package --vulnerable` + `npm audit` + اسکن APK (MobSF). پکیج آسیب‌پذیر = build قرمز.
9. **پرداخت:** فعلاً درگاه نیست. فقط **ثبت پرداخت قرارداد** (دستی، با فیش) در فاز ۳؛ اگر بعداً درگاه خواستند: Parbad + Ledger فقط-Insert + Idempotency (طبق بخش ۹ اسکیل‌ها).
10. **مشاهده‌پذیری:** Serilog + Seq، `/health/live` و `/health/ready`، OpenTelemetry، **Audit Log تغییرناپذیر** برای: تغییر نقش و مجوز، اصلاح ساعت کار، تأیید/رد غیبت، تغییر قیمت پکیج، حذف هر چیز.

## ۶. ماژول‌ها

### ۶.۱ نقش‌ها و مجوزها (دینامیک) — R12
- **مجوزها (Permissions) در کد ثابت‌اند** (کاتالوگ)، **نقش‌ها داده‌اند** و ادمین می‌سازد.
- هر مجوز **دامنه** دارد: `Own` (فقط مال خودش)، `Assigned` (کارهایی که به او سپرده شده)، `All`.
- کاتالوگ اولیه (قابل گسترش):

| گروه | مجوزها |
|---|---|
| کار | `work.view`, `work.create`, `work.assign`, `work.run`, `work.review`, `work.delete` |
| سفارش | `orders.view`, `orders.create`, `orders.manage` |
| مشتری | `clients.view`, `clients.manage`, `clients.contact` (دیدن شماره‌ی مشتری) |
| پکیج | `packages.view`, `packages.manage`, `packages.assign` |
| حضور | `attendance.self`, `attendance.view`, `attendance.approve`, `attendance.correct` |
| خدمات | `services.manage` (نوع خدمت، فیلدها، مراحل) |
| گزارش | `reports.view`, `reports.export` |
| تنظیمات | `settings.manage`, `languages.manage`, `content.manage` |
| کاربران | `users.manage`, `roles.manage` |
| تبلیغات | `campaigns.manage`, `influencers.manage` |

- **نقش‌های سیستمی** (پاک‌نشدنی): `Owner` (همه‌چیز، حداقل یک نفر، ۲FA اجباری) و `Client` (نوع کاربر جدا، فقط پورتال مشتری).
- نقش‌های نمونه‌ی Seed: «مدیر» (ادمین دوم)، «تدوینگر»، «عکاس و متن‌نویس»، «کار با هوش مصنوعی».
- یک کاربر می‌تواند **چند نقش** داشته باشد (ادمین که خودش تدوین هم می‌کند).
- **ضد IDOR:** شناسه‌ها `Guid`؛ هر Query با فیلتر دامنه‌ی مجوز (Global Filter یا Specification). کارگر فقط کارهای خودش؛ **شماره‌ی تماس مشتری را کارگر نمی‌بیند** (چون فقط ادمین با مشتری در تماس است) مگر با `clients.contact`.
- تغییر نقش‌ها با SignalR فوراً روی دستگاه کاربر اعمال شود (توکن بعدی مجوزهای جدید را دارد؛ صفحه‌ی باز منوی خود را به‌روز کند).

### ۶.۲ مشتری‌ها (Clients)
- نام کسب‌وکار، صنف، شخص رابط، موبایل، شهر، یادداشت داخلی (مشتری نمی‌بیند).
- **نوع مدیریت پیج:** `AgencyManaged` / `ClientManaged` (برای هر شبکه جدا).
- **حساب‌های شبکه:** برای هر پلتفرم (اینستاگرام، تلگرام، ایتا، بله، روبیکا، … — لیست دینامیک) آیدی/لینک. رمز پیج‌ها **ذخیره نشود**؛ اگر لازم شد، فقط یک فیلد «محل نگهداری رمز» (متن) — سیستم مدیر رمز نیست.
- پکیج فعال، تاریخ شروع/پایان، وضعیت قرارداد.
- ورود مشتری با **موبایل + OTP** یا **لینک دعوت یک‌بارمصرف** (ادمین می‌فرستد).

### ۶.۳ خدمات دینامیک (Service Types)
- ادمین «نوع خدمت» می‌سازد: ریلز، پست تکی، پست اسلایدی، استوری، کپشن، کمپین اینفلوئنسر، مدیریت ماهانه‌ی پیج، … و هر چیز جدید.
- برای هر نوع خدمت:
  - **فیلدهای فرم سفارش** (Form Builder): `text`, `textarea`, `number`, `date`, `datetime`, `select`, `multiselect`, `file`, `url`, `platform`, `color`. هر فیلد: برچسب (چندزبانه)، الزامی/اختیاری، راهنما، حداقل/حداکثر. ذخیره به‌صورت JSON Schema نسخه‌دار؛ **سفارش‌های قدیمی با نسخه‌ی قدیمی فرم** خوانده شوند.
  - **مراحل کار (Workflow):** لیست مرتب؛ هر مرحله: نام، **نقش مسئول**، زمان تخمینی، SLA (ساعت)، «نیاز به بازبینی ادمین»، «نیاز به تأیید مشتری».
  - قیمت پایه (اختیاری)، «از پکیج کم شود؟» و چند واحد.
- اعتبارسنجی فرم سفارش **سمت سرور** با همان Schema (نه فقط سمت کلاینت).

### ۶.۴ پکیج‌های فروش — R3
- **فیلدهای پکیج:**
  - نام (چندزبانه)، **شناسه‌ی کوتاه**، دسته (مثلاً «مدیریت پیج»، «تولید محتوا»، «تبلیغات»)
  - **قیمت** (`long` ریال)، **قیمت قبل از تخفیف** (اختیاری)، دوره: ماهانه / سه‌ماهه / یک‌باره
  - **سهمیه‌ها:** لیست «نوع خدمت × تعداد» (مثلاً ۱۲ پست، ۴ ریلز، ۸ استوری)
  - **شبکه‌های تحت پوشش** (چندانتخابی از لیست پلتفرم‌ها)
  - **نوع مدیریت پیج** پیش‌فرض (آژانس / مشتری)
  - تعداد جلسه‌ی مشاوره، تعداد اصلاح مجاز هر محتوا، زمان تحویل هر محتوا (ساعت)
  - **ویژگی‌ها** (لیست bullet چندزبانه)
  - **توضیحات کامل** (ویرایشگر متن غنی ساده: تیتر، پررنگ، لیست، لینک) — **HTML با Sanitizer سمت سرور** (فقط تگ‌های مجاز)
  - **فیلدهای سفارشی پکیج** (همان Form Builder، اگر صنفی چیز خاصی لازم داشت)
  - عکس کاور، ترتیب نمایش، فعال/غیرفعال، «پرفروش» (نشان)، نمایش در سایت عمومی بله/نه
- **پکیج مشتری (ClientPackage):** تخصیص پکیج به مشتری با تاریخ؛ **کپی منجمد (Snapshot)** از سهمیه و قیمت هنگام تخصیص (تغییر بعدی پکیج روی قرارداد قبلی اثر ندارد).
- **مصرف:** هر سفارش تأییدشده از سهمیه کم می‌کند (تراکنش اتمیک + همزمانی)؛ نوار «۸ از ۱۲ مانده» برای ادمین و مشتری. سهمیه تمام شد → سفارش جدید «خارج از پکیج» با هشدار برای ادمین.
- تمدید، ارتقا، پایان؛ یادآوری تمدید ۷ روز قبل (به ادمین).

### ۶.۵ سفارش‌ها و کارها (Orders & Work Items)
- سفارش از **مشتری** (از کاتالوگ خدمات در پورتال) یا از **ادمین** (برای مشتری) ثبت می‌شود.
- پذیرش ادمین → برای هر مرحله‌ی Workflow یک **WorkItem** ساخته می‌شود.
- **تابلوی کانبان لایو** (ستون‌ها = وضعیت‌ها)، فیلتر بر اساس مشتری، کارگر، نوع خدمت، ددلاین. Drag & Drop روی دسکتاپ؛ روی موبایل **منوی «انتقال به…»** (نه درگ).
- **سپردن کار:** پیشنهاد خودکار کارگر بر اساس نقش و حجم کار باز؛ ادمین با یک لمس تأیید.
- هر WorkItem: توضیح، فایل‌های مشتری، ددلاین، **کامنت داخلی** (مشتری نمی‌بیند) و **کامنت مشتری** (جدا)، تاریخچه.
- **تحویل:** کارگر فایل نهایی را آپلود می‌کند (آپلود قابل ادامه — بخش ۱۲) → «ارسال برای بازبینی» → ادمین تأیید یا رد با یادداشت → (اگر لازم) ارسال برای مشتری → تأیید یا «اصلاح لازم است».
- **انتشار (PublishJob):** برای هر محتوای تأییدشده: شبکه، **تاریخ و ساعت انتشار**، کپشن، هشتگ، فایل.
  - `AgencyManaged`: ادمین/کارگر بعد از انتشار «منتشر شد» + لینک پست.
  - `ClientManaged`: سر ساعت یادآوری به مشتری (اپ، ربات بله/تلگرام، پیامک) با **دانلود فایل** و **کپی کپشن**؛ مشتری «منتشر کردم». ۲ ساعت بعد بدون تأیید → `Overdue` و اعلان به ادمین.
- **تقویم محتوا:** نمای ماه/هفته برای هر مشتری و برای کل آژانس.

### ۶.۶ ساعت کار دقیق — R4
- **برنامه‌ی کاری (WorkSchedule)** برای هر کارگر: روزهای هفته، ساعت شروع/پایان، استراحت، **مهلت تأخیر** (مثلاً ۱۰ دقیقه)، تعطیلات رسمی (تقویم شمسی، از پنل). امکان «ساعت شناور» (فقط سقف ساعت هفتگی).
- **ورود و خروج (Clock in/out):** یک دکمه‌ی بزرگ در وب و اپ. **زمان مرجع = ساعت سرور**، نه گوشی.
- **استراحت:** «شروع/پایان استراحت».
- **تایمر کار:** روی هر WorkItem «شروع / مکث / تمام». قوانین:
  - تایمر فقط داخل شیفت باز کار می‌کند (اگر شیفت باز نیست: «اول ورود بزن»، یا تنظیم آژانس: شروع تایمر = ورود خودکار).
  - هم‌زمان فقط یک تایمر (ایندکس دیتابیس). شروع تایمر جدید = مکث خودکار قبلی.
  - خروج از شیفت = توقف خودکار تایمر.
  - **فراموشی:** اگر شیفت تا «پایان برنامه + X ساعت» باز ماند، سیستم به کارگر و ادمین هشدار می‌دهد؛ در پایان روز شیفت با وضعیت «نیازمند بررسی» بسته می‌شود (نه با حدس).
- **آفلاین:** اگر نت قطع بود، رویداد با `deviceTime` و **زمان سپری‌شده از ساعت یکنواخت دستگاه** در صف ذخیره و بعداً با **Idempotency-Key** ارسال می‌شود؛ سرور زمان را با اختلاف ساعت دستگاه اصلاح و با برچسب «ثبت آفلاین» نشان می‌دهد. اختلاف بیش از حد مجاز → «نیازمند تأیید ادمین».
- **اصلاح ساعت:** کارگر **درخواست اصلاح** با دلیل می‌دهد؛ ادمین با `attendance.correct` تأیید می‌کند. رکورد اصلی پاک نمی‌شود؛ اصلاح یک رویداد جدید است (Append-only) و در Audit.
- (اختیاری، Feature Flag خاموش) **محدودیت مکان یا شبکه** برای کارگرهای حضوری: ورود فقط از IP دفتر یا شعاع مکانی. از مشتری بپرس کارگرها حضوری‌اند یا دورکار.
- **داشبورد لایو صاحب‌کار:** چه کسی الان در شیفت است، روی کدام کار، چند دقیقه؛ چه کسی هنوز نیامده؛ چه کسی در استراحت است.
- **گزارش‌ها:** ساعت هر کارگر (روز/هفته/ماه)، تأخیر، اضافه‌کار، **ساعت صرف‌شده برای هر مشتری و هر نوع خدمت**، مقایسه با زمان تخمینی؛ خروجی Excel و PDF.

### ۶.۷ غیبت، مرخصی و تأخیر — R5
**انواع (دینامیک از پنل):** مرخصی استحقاقی، استعلاجی، ماموریت (کار بیرون)، غیبت موجه، غیبت غیرموجه، تأخیر، تعجیل در خروج. هر نوع: «با حقوق/بی‌حقوق»، «نیاز به مدرک»، سقف ماهانه/سالانه، رنگ.

**سناریوها:**
1. **درخواست از قبل:** کارگر «درخواست مرخصی» می‌دهد: نوع، **روزانه یا ساعتی**، **از تاریخ/ساعت تا تاریخ/ساعت**، **دلیل** (متن اجباری)، مدرک (اختیاری/اجباری طبق نوع). → اعلان لایو به ادمین → تأیید یا رد با یادداشت → اعلان به کارگر. تأییدشده در تقویم تیم دیده می‌شود و **پیشنهاد سپردن دوباره‌ی کارهای ددلاین‌دار** آن بازه را می‌دهد.
2. **غیبت اعلام‌نشده (تشخیص خودکار):** Job هر ۵ دقیقه: اگر شروع برنامه + مهلت تأخیر گذشت و ورود ثبت نشده و مرخصی تأییدشده‌ای نیست → رکورد `Absence` با وضعیت `Detected` + اعلان به کارگر («غیبت ثبت شد؛ دلیل را تا X ساعت بنویس») و به ادمین. اگر کارگر بعداً ورود زد → به **تأخیر** با مدت دقیق تبدیل می‌شود.
3. **ثبت دلیل بعد از واقعه:** کارگر دلیل + زمان واقعی (مثلاً «۹ تا ۱۱ دکتر») + مدرک → `ReasonSubmitted` → تصمیم ادمین (موجه/غیرموجه). بدون دلیل تا مهلت → خودکار «غیرموجه» (قابل تغییر ادمین با Audit).
4. **تعجیل در خروج:** خروج قبل از پایان برنامه → سؤال «دلیل؟» (اختیاری/اجباری طبق تنظیم).
5. **ثبت توسط ادمین:** ادمین برای کارگر مرخصی/ماموریت ثبت کند (مثلاً تلفنی خبر داده).
- **مانده‌ی مرخصی** هر کارگر از رویدادها محاسبه شود (نه فیلد قابل ویرایش).
- **تقویم حضور تیم** (ماهانه، رنگی) + گزارش ماهانه‌ی حضور و غیاب برای حقوق.

### ۶.۸ اعلان‌ها
- کانال‌ها: **داخل اپ (SignalR، لایو)**، **ربات بله** و **ربات تلگرام** (Bot API)، **پیامک** (کاوه‌نگار / sms.ir)، **پوش اندروید** از طریق `IPushProvider` (آداپتر: سرویس پوش ایرانی یا FCM — قبل از انتخاب، وضعیت فعلی سرویس را بررسی کن؛ پوش هرگز تنها کانال یک اعلان مهم نباشد).
- همه از طریق **Transactional Outbox** + Worker، با تکرار و Idempotency.
- هر کاربر کانال‌های دلخواهش را انتخاب می‌کند؛ «ساعات سکوت».
- اتصال ربات بله/تلگرام به حساب: با **کد یک‌بارمصرف** از داخل اپ (نه شماره‌ی تلفن).

### ۶.۹ پنل مشتری (Client Portal)
- خدمات فعال با **مرحله‌ی فعلی و درصد پیشرفت** (لایو).
- **سفارش خدمت جدید** از کاتالوگ (فرم دینامیک).
- **تأیید یا «اصلاح لازم است»** روی پیش‌نمایش محتوا (عکس/ویدیو با کیفیت کم برای پیش‌نمایش؛ اصل فقط با دکمه‌ی دانلود).
- **یادآوری انتشار** (برای پیج‌های دست خودش).
- مصرف پکیج، تقویم محتوای ماه، **گزارش ماهانه** (فاز ۲).
- مشتری **هیچ** کارگر، ساعت کار، یادداشت داخلی یا مشتری دیگری را نمی‌بیند.

### ۶.۱۰ چندزبانه‌ی دینامیک و محتوای دینامیک — R13

## ۸. لایو در کل سیستم — R14

- **Hub‌ها** (تایپ‌شده `Hub<IClient>`):
  - `WorkHub`: تابلو، کارها، سفارش‌ها
  - `PresenceHub`: شیفت، تایمر، حضور
  - `NotificationHub`
- **گروه‌ها:** `tenant:{id}`، `user:{id}`، `client:{id}`، `role:{id}`. هر کاربر فقط به گروه‌هایی وصل می‌شود که مجوزش را دارد (چک سمت سرور، نه کلاینت).
- **پیام‌ها کوچک (Delta):** فقط `{type, id, changedFields, version}`؛ نه کل شیء.
- **همگام‌سازی بعد از قطع:**
  - هر تغییر یک **شماره‌ی ترتیبی (Change Cursor)** دارد.
  - کلاینت بعد از اتصال دوباره `GET /api/v1/changes?since={cursor}` می‌زند.
  - اگر cursor خیلی قدیمی بود → بارگیری مجدد همان صفحه.
- **مدیریت اتصال:** اتصال دوباره با backoff و jitter. روی اپ: وقتی اپ به پس‌زمینه رفت، اتصال قطع شود (صرفه‌جویی باتری و داده) و برگشت = همگام‌سازی.
- **حالت آفلاین در UI:** نوار «آفلاین — تغییرات بعداً ارسال می‌شود»، و صف عملیات (ورود/خروج، تایمر، تأیید) با Idempotency-Key.

## ۱۱. ۱۰۰۰ کاربر همزمان — R8

**هدف قابل اندازه‌گیری (تست k6 در `tests/load/`):**
- ۱۰۰۰ اتصال SignalR همزمان + ۲۰۰ درخواست API در ثانیه به مدت ۱۵ دقیقه.
- **p95 API < 300ms**، خطا < ۰.۵٪، بدون قطع اتصال‌های انبوه.
- مصرف حافظه‌ی API پایدار (بدون نشت).

**چطور:**
- Kestrel پشت **Nginx** (تنظیمات WebSocket طبق مستندات مایکروسافت: `Upgrade`، `proxy_buffering off`)؛ SignalR روی سرویس API جدا از وب.
- **Redis backplane** از روز اول در کد (حتی با یک نمونه)؛ با بیش از یک نمونه: **sticky session** (`ip_hash`) یا **WebSockets-only + SkipNegotiation**.
- **PostgreSQL:** Connection Pooling (حد مناسب در connection string)، ایندکس روی همه‌ی فیلترها، کوئری‌های لیست با Projection، **بدون Lazy Loading**.
- **HybridCache + Redis** برای خواندنی‌های پرتکرار (نقش‌ها و مجوزها، ترجمه‌ها، تنظیمات، کاتالوگ خدمات)؛ باطل‌سازی با Tag.
- **RateLimiter:** OTP، ورود، آپلود، فرم‌ها، و هر کاربر (توکن باکت) — تا یک کلاینت خراب کل سرور را نگیرد.
- کارهای سنگین (پردازش عکس/ویدیو، گزارش Excel، پیامک) در **Worker** با صف؛ API فقط ثبت می‌کند.
- Response Compression (Brotli)؛ **Output Caching** برای endpointهای عمومی.
- **Health Check** و ری‌استارت خودکار کانتینر.
- اپ و وب: همه‌ی درخواست‌ها **Timeout** و **Retry با backoff**؛ UI هرگز روی درخواست شبکه قفل نشود (Skeleton، Optimistic UI با برگشت در خطا).

## ۱۴. امنیت — ۱۰ اسکیل + الزامات

- **ربات‌ها:** Webhook با توکن مخفی در مسیر + بررسی هدر؛ پیام ربات هرگز داده‌ی حساس (شماره، مبلغ) نفرستد.

- CI: CodeQL/Semgrep (اسکیل Trail of Bits)، `dotnet list package --vulnerable`، `npm audit`، **MobSF روی APK Release**، اسکن GitHub Actions.
